# 学びの記録（lessons）

このプロジェクトで得た「次回に活かす学び」をためておくメモ。

---

## 1. 公開サーバーでのデバッグは「画面表示」ではなく「保護ログ」に書く

- **きっかけ**：500エラーの原因調査で `ini_set('display_errors', 1)` を提案したが、
  ユーザーから「他の人に見えたらよくないのでは？」と正しい指摘を受けた。
- **学び**：本番・公開サーバーでエラーを画面表示すると、たまたま訪れた他人にも
  ファイルパスや設定が漏れる。**画面には出さず、外部からアクセスできない場所に記録**する。
- **やり方**：`display_errors=0` にして `error_log` を `data/debug.log` のような
  **.htaccess で保護されたフォルダ**へ向ける。調査が終わったら必ず削除する。

---

## 2. FileZillaで上げるPHPに「日本語コメント」を入れると壊れることがある

- **きっかけ**：`mail_config.php` をサーバーに上げたら 10行目で `syntax error`。
  ローカルのファイルは正常だったのに、サーバー上だけ壊れていた。
- **原因**：日本語（マルチバイト文字）のコメントが、転送やサーバー環境で崩れて文法エラーに。
  バイナリ転送にしても直らなかった。
- **学び**：サーバーに上げる設定ファイルは、**コメントを英語・記号のみのASCIIにする**と崩れない。
  値（接続情報）はそのままでOK。

## 3. 秘密情報は「GitHubには上げない／サーバーには上げる」

- `mail_config.php`（パスワード）と `data/users.csv`（個人情報）は `.gitignore` で除外。
- GitHub＝公開の場なので秘密はNG。レンタルサーバー＝動かす場所なので秘密は必要。
- `.gitignore` は「GitHubに送らない」設定であって、FileZillaの手動アップには影響しない。

## 4. 「誰が操作したか」をURLで受け取ってはいけない

- **きっかけ**：講義資料（PHP05）のいいね機能が `like_create.php?user_id=1&todo_id=3` と、
  **押した人のIDまでURLで送る**書き方だった。
- **問題**：URLの数字を書き換えるだけで、他人としていいねできてしまう。
  講義は「ログイン機能がない状態」を前提にした簡略版だった。
- **学び**：ログイン機能があるなら、**「誰が」はセッションから取る**（`$_SESSION['user_id']`）。
  URLで受け取っていいのは「何に対して」（`article_id` など）だけ。
- **見分け方**：URLのパラメータを書き換えて損をする人がいるなら、それはURLで渡してはいけない値。

## 5. 数えられる値は「列で持たず、そのとき数える」

- **きっかけ**：いいね数をどう保存するか。`articles` に `like_count` 列を足す案もあった。
- **問題**：列で持つと、いいねするたびに `like_table` と `articles` の**2か所を更新**する必要があり、
  片方だけ失敗すると数字がズレて、どちらが正しいか分からなくなる。
- **学び**：`GROUP BY` ＋ `COUNT()` で**毎回数える**。データの置き場所は1つに保つ。
  「あるデータを更新すると別のテーブルも更新が必要」はアンチパターンのサイン。

## 6. 一覧から行が消える結合と消えない結合がある

- **きっかけ**：いいね0件の記事が一覧から消えないようにしたかった。
- **学び**：`INNER JOIN` は**両方にデータがある行だけ**残るので、いいね0件の記事が消える。
  `LEFT OUTER JOIN` は左（記事）を全部残し、無い側は `NULL` になる。
- **セットで必要な処理**：`NULL` はそのまま表示すると空欄になるので、PHP側で `(int)` に変換して
  0 として表示する。
- **続き（マイページ実装で分かったこと）**：同じ `like_table` を使っていても、
  **目的が変わると結合の種類も変わる**。
  - 記事一覧＝全記事を並べたい → `LEFT OUTER JOIN`（0件の記事も残す）
  - マイページ＝いいねしたものだけ並べたい → `INNER JOIN`（無い記事は出なくて正しい）
  「どちらが正しい結合か」ではなく「**何を残したいか**」で選ぶ。

## 7. データベースの作業は「実行前に画面を1枚見る」と間違えない

- **きっかけ**：phpMyAdmin にSQLを貼るとき、ファイルの3分の1しか貼れていなかった。
  そのまま実行すると、表が1つだけ作られて記事が空のまま気づきにくい状態になっていた。
- **学び**：SQLを実行する前に、**どのデータベースを選んでいるか／貼った内容が最後まであるか**を確認する。
  今回のように似た名前の練習用DB（`gs_php_db`）が並んでいると、入れる場所を間違えやすい。
- **注意**：phpMyAdmin の「**完了した後、ロールバック**」にチェックが入っていると、
  実行しても結果が残らない（お試し用の機能）。
